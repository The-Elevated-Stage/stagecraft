# Hybrid XML/Markdown Document Structure — Design Document

**Date:** 2026-02-18
**Status:** Design Complete
**Type:** Cross-cutting convention (affects skills, task instructions, plans, config)

---

## 1. Problem Statement

Claude-consumed documents in this project use pure markdown with authority
signaled through ALL-CAPS keywords (MANDATORY, CRITICAL, [STRICT]) and bold
formatting. This approach has three systemic problems:

**Authority differentiation failure.** Rules embedded in paragraphs alongside
explanatory context are consistently ignored. Documented failure modes include:
musicians not launching background message-watchers, copyists not following
templates, conductors not using prescribed launch commands, MEMORY.md structure
being clobbered, `/tmp/` being accessed despite rules mandating `temp/`, and
Obsidian notes being read directly instead of following the scan-then-read
workflow. The failure is always in one direction — rules treated as optional,
never guidance treated as mandatory.

**Context overload.** Large documents (500+ lines) overwhelm Claude's attention.
Musicians never self-monitor context usage, ignore prescribed inflation estimates,
and never voluntarily stop work — requiring human intervention to cut sessions off.
Rules placed far from the execution point where they apply get forgotten.

**Cross-file inconsistency.** Each document type uses different conventions for
authority signaling, section structure, and template enforcement. No shared
structural vocabulary exists across skills, task instructions, and plans.

---

## 2. Solution: Three-Tier Document Format

A three-tier system based on document audience, with XML tags providing
structural authority signals and navigation:

| Tier | Format | Audience | Default? |
|------|--------|----------|----------|
| **Tier 1** | Pure Markdown | Primarily human-consumed, maybe Claude-reviewed | No |
| **Tier 2** | Hybrid Markdown + XML | Claude-consumed or shared (human-reviewable) | **Yes — default** |
| **Tier 3** | Full XML envelope with Markdown content | Exclusively or primarily Claude-consumed | No |

**Tier 2 is the default.** Tier 1 is the exception for human-focused documentation.
Tier 3 is for complex Claude-only documents where full structural control is needed.

### Tier Selection Decision Tree

1. Is this primarily human-consumed (designs, specs, READMEs)? → **Tier 1**
2. Is this Claude-consumed or shared? → **Tier 2** (default)
3. Is this exclusively Claude-consumed with complex structure? → **Tier 3**

Edge cases:
- If unsure between Tier 1 and 2, choose Tier 1. Human readability is the default.
- If unsure between Tier 2 and 3, choose Tier 2. Hybrid is sufficient for most shared documents.
- Simple skills (single workflow, <300 lines) → Tier 2. Complex skills (conditional scenarios, >300 lines, many references) → Tier 3.
- RAG entries → Tier 1 by default. Tier 2 only if the entry has multiple sections with different authority levels or cross-references.

## 3. Document Type Classification

### Tier 1: Pure Markdown

- Design documents (Dramaturg/brainstorming output)
- Reference designs (`docs/reference/designs/`)
- README files
- Feature specs (`docs/specs/`)
- Scratchpad files (`docs/scratchpad/`)

### Tier 2: Hybrid Markdown + XML

- Implementation plans
- Skill SKILL.md files (musician, copyist — Tier 2 by design choice even when >300 lines, as the hybrid format maintains readability without full XML envelope)
- RAG entries with cross-references or authority-level language (optional)

### Tier 3: Full XML Envelope

- Task instruction files (generated by copyist, consumed by musician)
- CLAUDE.md (Claude edits, Claude reads every turn)
- Complex skill SKILL.md files (Conductor, future complex skills)
- All non-SKILL.md skill files (references, templates, examples)
- Copyist templates (sequential/parallel task templates)
- Dramaturg/Arranger decision journals
- Proposals (`docs/implementation/proposals/`)
- Completion reports
- Memory graph entities (if applicable)

## 4. Tag Vocabulary

Ten tags in two categories. Every tag contains markdown inside it — XML is
structure, markdown is content.

### Authority Tags

Authority tags define **how Claude should treat** the enclosed content. They can
appear as blocks (wrapping a section of content) or inline (flagging a specific
statement within a flow).

**`<mandatory>`** — Non-negotiable constraint. Must follow exactly. No adaptation,
no approximation. Violations are task failures.

```xml
<!-- Block usage: collected rules -->
<mandatory>
- Must launch background message-watcher before any work step
- Must check system message context usage after every tool response
- Must use `temp/` for scratch files — never `/tmp/` directly
</mandatory>

<!-- Inline usage: reinforcement at point of relevance -->
<mandatory>Background message-watcher must be running at all times.</mandatory>
If watcher is not running, relaunch immediately before continuing.
```

**`<guidance>`** — Recommended approach. Can adapt to context, but deviations
should be conscious and justified — not accidental omissions.

```xml
<guidance>
Read files in dependency order — models before services before screens.
If a file exceeds 500 lines, read the relevant section via offset/limit.
</guidance>
```

**`<context>`** — Background information for understanding. No behavioral mandate.
Claude should internalize this but is not required to act on it.

```xml
<context>
The orchestration system uses SQLite with WAL mode. The comms-link MCP
server provides database access. WAL isolation means comms-link cannot
see changes made by external sqlite3 processes.
</context>
```

### Structural Tags

Structural tags define **how Claude should navigate and use** the content.

**`<sections>`** — Section index / table of contents. Lists all `<section id="...">`
values in the document in order. Must appear near the top of the document, after
metadata/frontmatter.

```xml
<sections>
- mandatory-rules
- bootstrap-workflow
- execution-steps
- review-checkpoint
- error-recovery
</sections>
```

**`<section id="...">`** — Named, findable section. The `id` enables scanning —
Claude can locate a section by ID without reading the entire document linearly.

```xml
<section id="bootstrap-workflow">
## Bootstrap Sequence
[... content ...]
</section>
```

**`<core>`** — Essential content. The substance of the work — objectives, workflow
steps, deliverables, structure. Distinguishes "this is what you're here to do"
from explanatory material around it. In Tier 2, `<core>` is optional — use it
when a section genuinely mixes essential and non-essential content. In Tier 3,
`<core>` is required — all text must be inside a tag (see Guideline 7).

```xml
<core>
## Objective
Implement the notification service with FCM integration.

## Deliverables
- `lib/services/notification_service.dart`
- Unit tests with 90%+ coverage
</core>
```

**`<template follow="exact|format">`** — Content that must be reproduced.
`exact` means verbatim with only placeholder values changed. `format` means
keep the data shape but generate new content within that shape.

```xml
<template follow="exact">
```sql
INSERT INTO orchestration_messages (task_id, from_session, type, message)
VALUES ('[task-id]', '$CLAUDE_SESSION_ID', 'status', '[message]');
```
</template>
```

**`<reference path="..." load="required|recommended">`** — External document that
should be loaded. `required` means must read before proceeding. `recommended`
means read if relevant.

```xml
<reference path="docs/knowledge-base/database/schema.md" load="required">
Database schema reference — needed for all migration work.
</reference>
```

**`<metadata>`** — Machine-readable execution parameters. Used in Tier 3
documents to replace YAML frontmatter. Contains structured key-value pairs
(dependencies, token estimates, safety flags). Tier 3 only — Tier 2 uses YAML
frontmatter for this purpose.

```xml
<metadata>
parallel-safe: true
dependencies: task-01, task-02
token-estimate: ~45k
review-checkpoints: 1 (after implementation)
</metadata>
```

**`<checkpoint>`** — Explicit pause point. Stop current work, verify the stated
condition, report status before continuing. Checkpoints carry the same authority
weight as `<mandatory>` — skipping a checkpoint is a task failure.

```xml
<checkpoint>
Verify: background watcher subagent is running (check task ID).
Check system message for current context usage.
If over 70%, prepare handoff scenario before continuing.
</checkpoint>
```

### Tag Relationship Rules

**Authority tags nest inside structural tags.** `<mandatory>`, `<guidance>`, and
`<context>` can appear inside `<core>`, `<section>`, `<template>`, or any other
structural tag. This is the primary pattern for inline usage.

```xml
<core>
### Step 3: Create NotificationService

<mandatory>Background message-watcher must be running.</mandatory>
If watcher is not running, relaunch immediately.

- [ ] <mandatory>File compiles without errors</mandatory>
- [ ] GetIt registration added to service_locator.dart
</core>
```

**Authority tags do not nest inside each other.** No `<mandatory>` inside
`<guidance>`, no `<context>` inside `<mandatory>`. Each statement has one
authority level. Contradictory nesting sends conflicting signals.

## 5. Tier 2 Template — Hybrid Markdown + XML

Tier 2 keeps YAML frontmatter for human-editable metadata, uses the section
index for navigation, and weaves authority/structural tags into normal markdown.
The document still reads like markdown — the tags add structure without dominating.

### Skeleton

```markdown
---
title: [Document Title]
date: YYYY-MM-DD
type: [plan|skill|rag-entry]
---

<sections>
- mandatory-rules
- overview
- phase-1
- phase-1-checkpoint
- phase-2
- success-criteria
</sections>

# Document Title

<section id="mandatory-rules">
<mandatory>
- [Hard constraint 1]
- [Hard constraint 2]
- [Hard constraint 3]
</mandatory>
</section>

<section id="overview">
<core>
## Overview

**Goal:** [1-2 sentences]

<reference path="[design-doc-path]" load="required">
[What this reference contains and why it's needed]
</reference>
</core>

<context>
[Background — where this came from, what preceded it]
</context>
</section>

<section id="phase-1">
## Phase 1: [Name]

<core>
### Task 1-A: [Description]

<mandatory>[Inline constraint specific to this task]</mandatory>

[Implementation details in normal markdown]

### Task 1-B: [Description]
[...]
</core>

<guidance>
[Approach recommendations, patterns to follow]
</guidance>

<checkpoint>
[What to verify before proceeding to next phase]
Check system message for current context usage.
</checkpoint>
</section>

<section id="success-criteria">
<core>
## Success Criteria

- [ ] [Criterion 1]
- [ ] [Criterion 2]
</core>
</section>
```

### Key Patterns

- **Tags wrap content, they don't replace markdown.** Headings, lists, code blocks
  remain markdown inside the tags.
- **Authority tags appear where needed, not everywhere.** A straightforward section
  might only have `<core>`. A complex section adds `<guidance>`, `<context>`, and
  inline `<mandatory>` tags.
- **The section index is the navigation map.** A downstream consumer can scan the
  index, identify relevant sections, and read only those.
- **`<reference>` tags appear inline** where the reference is needed, not in a
  separate references section at the bottom. The reference is next to the content
  that depends on it.

## 6. Tier 3 Template — Full XML Envelope

Tier 3 wraps the entire document in a typed XML envelope. No YAML frontmatter —
metadata lives in an XML tag. Every section is XML-wrapped. Markdown handles
content formatting inside the tags.

**Strict content rule:** In Tier 3, all text must be inside a tag. No "naked"
markdown floating outside of `<core>`, `<mandatory>`, `<guidance>`, `<context>`,
or `<template>`. This forces the author to explicitly classify every paragraph,
maximizing the authority structure's effectiveness.

### Document-Level Wrappers

Each document type gets a named wrapper:

| Wrapper | Used For |
|---------|----------|
| `<task-instruction>` | Task instruction files |
| `<skill>` | Complex skill files and skill reference files |
| `<config>` | CLAUDE.md, project configuration |
| `<journal>` | Dramaturg/Arranger decision journals |
| `<proposal>` | Proposals |
| `<report>` | Completion reports |

### Task Instruction File Skeleton

execution flow — at every point where a rule commonly gets violated.

## 7. Usage Guidelines

### Guideline 1: Authority Tag Discipline

**Block vs. inline usage:**
- Every document with authority tags must have **one collected `<mandatory>` block**
  near the top (inside `<section id="mandatory-rules">`). This is Claude's upfront
  "internalize all rules" pass.
- **Inline `<mandatory>` tags reinforce** specific rules at the point of execution.
  These repeat or narrow rules from the top block. The top block is the source of
  truth; inline tags are structural reminders.
- `<guidance>` and `<context>` are primarily block-level but can appear inline for
  short annotations.

**Avoiding dilution:**
- `<mandatory>` is reserved for things that are genuinely non-negotiable.
- Test for `<mandatory>`: "If Claude ignores this, is the task broken?"
  Yes → `<mandatory>`. No → `<guidance>` or `<core>`.
- Test for `<guidance>` vs. `<context>`: "If Claude ignores this, will the output
  be noticeably worse?" Yes → `<guidance>`. No → `<context>`.
- A document with 30 mandatory rules has a dilution problem. Aim for the smallest
  set of hard constraints that prevent actual failures.

**Nesting rules:**
- Authority tags nest freely inside structural tags. `<mandatory>` inside `<core>`
  is the primary pattern for inline usage.
- Authority tags do not nest inside each other. No `<mandatory>` inside `<guidance>`.
  Each statement has one authority level.
- `<template>` can appear inside any authority or structural tag.

### Guideline 2: Section Index as Navigation Contract

- Every Tier 2 and Tier 3 document must have a `<sections>` index after
  metadata/frontmatter.
- The index lists every `<section id="...">` in document order.
- If a section exists in the document but isn't in the index, it's a bug.
- Claude processing a large document should read the index first, identify relevant
  sections, then read those sections selectively.

### Guideline 3: Templates Are Behavioral Contracts

- `<template follow="exact">` — reproduce verbatim. Only placeholder values
  (marked with `[brackets]` or `'$VARIABLE'`) change. "Exact" means structure,
  variable names, and semantics must match. Formatting (whitespace, line breaks)
  and comments are flexible.
- `<template follow="format">` — keep the data shape (SQL columns, report headers,
  JSON keys, section structure) but generate new content within that shape.
- Every SQL state transition, subagent launch pattern, and commit command with a
  required format must be wrapped in `<template follow="exact">`.

### Guideline 4: Checkpoints as Structural Interrupts

- `<checkpoint>` means **stop and verify before proceeding**. Not a suggestion.
- Checkpoints must include specific verification commands or queries.
- For musician sessions, every checkpoint should include context usage monitoring:
  ```xml
  <checkpoint>
  [Task-specific verification]
  Check system message for current context usage.
  If over 70%, prepare handoff scenario before continuing.
  </checkpoint>
  ```
- Place checkpoints after every major work step, not just at review boundaries.

### Guideline 5: Context Overload Mitigation

**For document authors:**
- Front-load mandatory rules. The collected `<mandatory>` block must be the first
  section after metadata. Claude's attention is strongest at the beginning.
- Use inline `<mandatory>` tags at every point where a rule commonly gets violated.
- Keep `<context>` sections brief. If context runs long, move details to a
  `<reference>` and summarize inline.

**For Claude consuming these documents:**
- Read `<sections>` index first to understand document structure.
- Read `<section id="mandatory-rules">` in full before any other section.
- Use section `id` attributes for targeted reads — don't read linearly through
  sections that aren't needed.
- Treat inline `<mandatory>` tags as interrupt signals — pause, process, continue.
- At every `<checkpoint>`, stop and perform the verification. Do not read past a
  checkpoint without completing it.

### Guideline 6: Tier Selection

| Question | Answer | Tier |
|----------|--------|------|
| Is this primarily human-consumed? | Yes | Tier 1 |
| Is this Claude-consumed or shared? | Yes | **Tier 2 (default)** |
| Is this exclusively Claude-consumed with complex structure? | Yes | Tier 3 |

- Default to **Tier 2** when uncertain.
- Simple skills (<300 lines, single workflow) → Tier 2 SKILL.md.
- Complex skills (>300 lines, conditional scenarios, many references) → Tier 3.
- All non-SKILL.md skill files (references, templates, examples) → Tier 3.
- RAG entries → Tier 1 by default. Tier 2 only for multi-section entries with
  authority differentiation or cross-references.

### Guideline 7: Tier 3 Strict Content Rule

In Tier 3 documents, **all text must be inside a tag.** No unmarked markdown
floating inside a `<section>`. Every paragraph is explicitly classified as
`<core>`, `<mandatory>`, `<guidance>`, or `<context>`. This forces the author
to make a categorization decision for every piece of content, maximizing the
structural signal.

In Tier 2 documents, untagged text inside a `<section>` is acceptable. Tags
are used where they add value, not reflexively on every paragraph.

### Guideline 8: Tag Allowlist

Allowed tags: `mandatory`, `guidance`, `context`, `sections`, `section`, `core`,
`template`, `reference`, `checkpoint`, `metadata`, and document-level wrappers
(`task-instruction`, `skill`, `config`, `journal`, `proposal`, `report`).

**All other tags are forbidden.** Do not invent tags like `<warning>`, `<note>`,
`<important>`, `<example>`, or `<info>`. If content doesn't fit an existing tag,
it belongs inside `<core>`, `<guidance>`, or `<context>` with appropriate markdown
formatting inside.

---

## 8. Enforcement Strategy

These conventions must be reinforced across the project's knowledge systems:

- **CLAUDE.md** — Add tier selection rules and tag vocabulary reference to the
  universal rules section (in Tier 3 format once migrated).
- **RAG knowledge base** — Create entries for tag vocabulary, tier templates, and
  usage guidelines so future sessions can query them.
- **Memory graph** — Add project rules for hybrid document structure conventions
  with pointers to RAG entries.
- **Skill files** — Update skill authoring guidance (writing-skills skill) to
  include tier selection and tag usage for generated documents.
- **Copyist skill** — Update templates and generation rules to produce Tier 3
  task instruction files with inline `<mandatory>` tags.

## 9. Summary

| Component | Decision |
|-----------|----------|
| **Tag count** | 10 (3 authority + 7 structural) |
| **Authority tags** | `<mandatory>`, `<guidance>`, `<context>` |
| **Structural tags** | `<sections>`, `<section>`, `<core>`, `<template>`, `<reference>`, `<checkpoint>`, `<metadata>` |
| **Tier 1** | Pure markdown — designs, specs, READMEs, scratchpad |
| **Tier 2** | Hybrid — implementation plans, simple skills |
| **Tier 3** | Full XML — task instructions, CLAUDE.md, complex skills, journals, proposals, reports, skill references/templates |
| **Tier 3 strict rule** | All text must be inside a tag — no naked markdown |
| **Tag allowlist** | Only defined tags permitted — no invented tags |
| **Default tier** | Tier 2 |
| **Inline authority** | `<mandatory>` used inline throughout execution flows at violation-prone points |
| **Context monitoring** | `<checkpoint>` with 70% context threshold for handoff preparation |
| **Template enforcement** | `<template follow="exact\|format">` replaces [STRICT]/[FLEXIBLE] convention |
